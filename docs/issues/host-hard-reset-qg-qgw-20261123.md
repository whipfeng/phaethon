## 宿主侧证据（qgw / WQPC，Win7）

- Event 6008：上一次关机时间为 2026-11-23 13:57:33，标记为**意外**；
- Event 41（Kernel-Power）：`BugcheckCode=0`、`BugcheckParameter1..4=0x0`、
  `SleepInProgress=false`、`PowerButtonTimestamp=0`；
- 最近一次 Event 1074（主动关机/重启）为 2026-06-03；13:57 前后没有任何
  1074 / 6006 记录 —— 说明内核**从未走到关机流程**（手工按电源键时若内核
  还活着，ACPI 电源键事件会被处理并产生 1074；现在没有，反证按下时内核/桌面
  已经死锁）；
- 无 `C:\Windows\MEMORY.DMP`，无 minidump；Application 日志无 phaethon 的
  1000/1001/1026；仅有的 1001 是 `WindowsUpdateFailure3`（SafeLink.exe），无关；
- phaethon 日志最后一行 13:57:43 后直接截断，进程没有机会写退出/panic 信息；
- `PowerButtonTimestamp=0` 同样说明：内核在本次复位周期里没有记录到一次
  正常的 ACPI 电源键事件，符合“系统已卡死 → 人工强制断电”的场景。

## 新增事实对结论的修正（2026-11-23 用户现场确认）

用户确认：**先发现系统卡死无响应，之后手动按了一次物理开关**。据此修正：

1. 本次不是“瞬间掉电”，而是 **先卡死、后人工强制断电**。13:57:33 ~ 14:2x
   之间系统已经处于不可用状态，Event 6008 的“意外关机”时间戳对齐的是
   断电那一刻，而不是卡死那一刻；
2. 因为没有 dump，仍然**无法区分**以下两种卡死形态：
   - 内核硬锁死（hard lockup，未触发 bugcheck）：不会有 BugCheck 事件、
     不会写 dump，与现有证据完全一致；
   - 已进入 BSOD 但 dump 写入未完成（磁盘/存储驱动一并卡住），或用户在看到
     蓝屏后、dump 落盘前就断电：同样不会留下 dump。
   现有证据只能证明“复位周期里 BugcheckCode=0”，不能证明“从未蓝屏”；
3. 不变的部分：phaethon 日志在宿主冻结前正常输出、无 panic/fatal、无 WER，
   watchdog 也没有主动重启记录 —— 应用侧仍未发现主动崩溃路径；
4. `AutoReboot=False`：即使真的蓝屏，机器也会停在蓝屏画面而不自动重启，
   这与用户看到“卡死”的现场表现一致，也解释了为什么必须人工断电。

### 补充核查结果（2026-11-23 通过 qgw 内置 SSH 复核）

- WER 提供程序 `Microsoft-Windows-WER-SystemErrorReporting` **已注册**（不是
  提供程序缺失导致的假阴性）；
- System 日志最近 2000 条中**没有任何 Event 1001 `BugCheck`** → 本次复位
  周期内确实没有走完 bugcheck；
- `C:\Windows\Minidump` 存在但文件数 = 0；`C:\Windows\LiveKernelReports`
  存在但递归文件数 = 0；`C:\Windows\MEMORY.DMP` 不存在；
- 结论收敛：**内核在冻结时连 bugcheck 都没走完**（或根本没触发），这与
  “硬锁死（hard lockup）”一致；仍不能排除“屏幕停在蓝屏但 dump 未落盘前被
  断电”，因为现场没有留下屏幕照片。

### 下次复现时的动作

- 先看屏幕并拍照（是否停留在蓝屏画面）——这一条能直接判定“硬锁死”还是“蓝屏”；
- 若在蓝屏画面上，等 dump 进度到 100% 再断电，否则每次都会拿到“无 dump”
  这个二义性结论；
- 记录按下电源键的精确时间，便于和 Event 6008 时间戳对齐；

### 关于“会不会是应用引发的系统级卡死”

- qgw 上 phaethon 是**纯用户态进程**且 `tun.enabled=false`，没有加载 wintun
  或任何自研内核驱动；用户态进程要让整机硬锁死，只能经由内核网络栈 /
  文件系统 / 存储驱动的缺陷，目前没有任何证据指向这条路径；
- phaethon 侧无 panic、无 WER、无资源耗尽记录，日志在冻结前正常滚动；
- 卡死同时带走 qgw 宿主和其上的 QG（Linux VM）：两个操作系统一起失去响应，
  更像宿主级（硬件 / 供电 / 宿主内核）事件，而不是单个用户态进程崩溃；
- 该结论是排除性判断，不是证明。若后续在**加载了 wintun/tun 的节点**上再次
  出现同类卡死，需要把内核驱动栈纳入排查（driver verifier + 现场 dump）。

- 卡死现场**先拍照、等 dump 写完再断电**；只要人工直接断电，就永远拿不到

- 复现时按上面“补充核查结果 / 下次复现时的动作”抓一遍：System 日志 1001

- 供电 / PDU / UPS 排查继续保留，但优先级下调：本次已确认有人工断电动作，
  不能再把 BugcheckCode=0 直接当成外部供电证据；
- 应用侧无法防御宿主编排外的强制断电（进程没有退出机会），现有 watchdog +
  开机自启动已能在宿主恢复后自动拉起；
- 后续再发生，优先看宿主事件日志（6008/41/1074）、dump 与供电记录，
  而不是先怀疑应用。

## 经验

- 多个节点同时失联，先画“节点 → 宿主 / VM”关系图：同一宿主上的 VM 会一起消失；
- Event 41 `BugcheckCode=0` + 无 1074 + 无 dump **只能**说明“复位周期内没有
  完成 bugcheck 重启”，既可能是硬锁死，也可能是蓝屏后 dump 未落盘；
  **必须先问现场是否人工断电**，否则结论会反过来；
- 手工按电源键却没有任何 1074 / ACPI 电源键记录，本身就是“内核当时已经死了”
  的强证据；
- 应用日志“最后一行直接截断”是宿主级冻结/断电的典型特征，但不能区分两者。
